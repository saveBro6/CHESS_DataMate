# /improve — Principal Refactor & Continuous Improvement

**Phase 6 of 6.** The feature works and is tested. Now make the *system* better, and make the
next run cheaper than this one.

## 0 · Gate

```bash
bin/sdlc gate <slug> improve     # requires 05-test-report.md → result: ALL_PASSED
```

Refactoring on a red suite is guesswork. Blocked gate → back to `/test`.

## 1 · Read the whole run as evidence

Read `03-execution.md`, `04-review.md`, `05-test-report.md`, `02-plan.md` (including its
Deferred section). Then delegate the analysis: persona
`.agent-sdlc/agents/principal-refactorer.md` plus those artifacts. Ask it for a ranked list of
candidates, each with evidence and a risk rating.

Look for, in priority order:

1. **Defects the review only mitigated** — a `[MINOR]` that was really a design smell.
2. **Duplication** the diff introduced (copy-pasted branches, near-identical helpers).
3. **Performance**: needless O(n²), repeated I/O, re-computation in loops, unbounded growth.
4. **Dead code / unused exports / vestigial flags** left by the change.
5. **Test-suite friction**: slow, flaky, or over-mocked tests that will tax every future run.
6. **Missing guardrails**: a bug class from this run that a lint rule or check would catch.

## 2 · Refactor safely, or not at all

Apply only refactors that are (a) behaviour-preserving, (b) provable by the existing suite,
(c) contained. For each one:

```bash
<test command>            # baseline — must be green BEFORE you start
<edit>
<test command>            # must still be green, same or more tests
<lint> && <typecheck> && <build>
```

Any behavioural change is a **new feature**, not a refactor: it belongs in a new `/brainstorm`
run with its own spec and gate chain. Saying that out loud is the correct outcome.

## 3 · Write `06-improve.md`

Fill the template: what changed and why, before/after measurements where you have them,
what you deliberately did **not** touch (with reasons), and the residual debt.

## 4 · Feed the loop back

The most valuable output is a **proposed rule** that prevents this run's mistakes from
recurring — a line for `AGENTS.md` or the project's coding guidelines. Propose them in a
dedicated `## Proposed rule updates` section of `06-improve.md` as a unified diff against the
target file. **Do not edit `AGENTS.md` directly**: rule changes are a human decision
(`bin/sdlc set` is for artifacts, not for the project constitution).

## 5 · Close the run

```bash
bin/sdlc set <slug> 06-improve.md status=COMPLETE
bin/sdlc advance <slug>          # → done
bin/sdlc validate <slug>         # final consistency check
```

Report: refactors applied, tests still green (with the real command output), lessons learned,
and the proposed rules awaiting human approval.

## Hard rules

- **Green suite before and after**, or you have not improved anything.
- **No scope creep** — "while we are here, let's also add…" belongs in the next run's spec.
- **No rule changes without approval.** Propose the diff; let the human merge it.
- **No self-graded victory.** If the only improvement you can find is "nothing", write that,
  with the evidence you checked — an honest empty result is more useful than a cosmetic churn.
